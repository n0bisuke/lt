`inbox/` の素材から、発表者が見て直せる下書きのデッキを作ります。最初に `AGENTS.md` と `design-system/project/README.md` を読み、デザインと言葉のルールはそれに従います。

発表者は素材を入れて呼ぶだけで済ませたいので、途中で質問せず最後まで作ります。分からないことは「【要確認】」としてデッキに残し、完成したデッキと一緒に聞きます。実物を見ながらのほうが答えやすいからです。

## 手順

1. **素材を確かめる。** `inbox/` を一覧します（`_used/` は処理済みなので除きます）。素材がなく、話の中にネタもなければ、`inbox/` に入れるよう伝えて終わります。
2. **デッキ名を決める。** 日付は発表者の言葉かメモから取り、なければ今日にします。名前は内容を表す短い英小文字にします。発表者が既存のデッキへの追加を頼んだときは、そのデッキ名を使います。内容が見えないうちに決められなければ `<日付>_draft` で取り込み、画像を見てからフォルダ名を変えます。
3. **取り込む。**

   ```bash
   node scripts/new-deck.mjs <YYYYMMDD_name> --title "仮のタイトル"
   ```

   注意が表示されたら、最後の報告に含めます。
4. **素材をすべて見る。** `images.md` の画像を1枚ずつ開き、`notes/` を読みます。ファイル名だけで判断すると、写っていないことを書いてしまいます。
5. **話を組み立てる。** 画像の順番は撮った順なので、多くの場合はそのまま作業の流れです。写っているものから「何を試して、どこで苦戦して、どうなったか」を読み取り、README の「デッキの構成」に当てはめます。
6. **デッキを書く。** `deck.md` を `design-system/project/marp.md` の書き方で書きます。1つのファイルからスライド、記事、PDF ができるので、話す内容は発表者ノート（`<!-- -->`）に書きます。イベントページの URL があれば先頭の `eventUrl` に入れ、なければ「【要確認】」として最後に聞きます。素材は話に合う場所に使い、合わないものは無理に使わず報告します。
   - 写っていて確かなことは言い切ります。
   - 推測した動機、結果、感想、数値は書き切らず、「【要確認】」を付けます。結果を良く書いて話を完結させないでください。発表者が試していないことがスライドに残るのがいちばん困ります。
   - 自己紹介の最後の1行は、メモになければ「【要確認】最近のネタ」にします。
   - 足りない素材は `lt-slot` に、何を撮れば良いかを具体的に書きます。
7. **書き出して目で確かめる。**

   ```bash
   scripts/export-pdf.sh decks/<デッキ名>
   ```

   `deck.html?overview` か PDF で全ページを見て、文字のはみ出し、タイトルの折り返し、画像との重なりを直します。
8. **報告する。** 次の順で短く伝えます。
   - デッキと PDF のパス、枚数
   - 読み取った話の流れ（1〜2行）
   - 「【要確認】」の質問（スライド番号付き）
   - 残っている `lt-slot`、使わなかった画像、取り込み時の注意

公開とコミットは、発表者が頼むまでしません。下書きには推測が混ざっているからです。頼まれたら `AGENTS.md` の「公開する」に従います。
